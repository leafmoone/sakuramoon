## Worker contract

- Launch the exact schema-v3 `worker_count` as persistent DataLoader workers. The
  requested count must equal the coordinator store count; there is no topology drift
  or fallback to one worker.
- Keep the D022 state store and shard cache exclusively in the parent. Workers receive
  only an immutable D021 `ShardRecord` and one already-prepared absolute local path.
- Give each worker a private capacity-one shard command queue. DataLoader ready output
  remains bounded by the explicit divisible ready-batch budget, and the completion
  channel is bounded by `worker_count`.
- Create every command/completion queue and every DataLoader worker from one explicit
  `spawn` context. Default `fork`, mixed contexts, and fallback to one worker are
  forbidden; a live PyTorch parent thread must not prevent worker progress.
- Disable WebDataset's worker splitter only for parent-partitioned leased clones. This
  prevents a trusted one-shard assignment from being split a second time by global
  worker identity while leaving the ordinary pipeline entry point unchanged.
- Use unordered DataLoader result delivery for the command-driven workers. Worker
  identity is carried on every batch/done message, so a blocked idle worker task cannot
  prevent another worker's next assigned shard from reaching the parent.
- Mark a shard complete only after its batches, ordered per-worker done marker, and
  normal completion-channel message have all reached the parent. A worker exception,
  `os._exit`, or parent iterator close never calls `mark_completed`.
- Reorder only for the D022 recovered-active barrier: all recovered active shards must
  be explicitly requested, re-prepared, and assigned before a new shard is activated.
  Restart replay remains whole-shard at-least-once and queues are not serialized.

## Evidence

- D023 persistent-worker and fault contracts: 5 passed. The tests assert worker IDs
  `{0,1}`, two distinct process IDs reused across four shards, input capacity one per
  worker, ready prefetch one per worker, completion capacity two, and one shared
  explicit `spawn` context for queues and DataLoader processes.
- The exact independent-review reproducer (`D022 state` followed by D023 worker/fault
  tests) completed 26 tests in 20.54 seconds under a 120-second process timeout. The
  first worker test kept a real PyTorch CPU thread alive while both spawned workers
  processed four shards; the previous implicit-`fork` implementation hung twice at
  this boundary.
- A real DataLoader worker `os._exit(23)` left both prepared shards active. A fresh
  coordinator counted exactly two replayed shards/two samples, re-prepared both, and
  replayed both samples from shard start before completion.
- Closing the parent batch generator after the first delivered batch left both
  prefetched shards active; restart replayed both from the beginning.
- A recovered-active test rejects worker-count fallback before cache/state mutation,
  prepares both recovered shards before the third shard, and preserves full active-set
  cache protection.
- Cache/state/pipeline/collate/fault adjacency produced 65 passes. The unrelated
  pre-existing T054 download-SIGKILL case missed its fixed 5-second readiness barrier:
  a fresh subprocess needed approximately 7-10 seconds merely to import its existing
  modules in this environment. D023 does not modify that driver or claim it passed.
- Ruff passed. Pyright reported 0 errors and 0 warnings for the D023 implementation and
  targeted tests.
- Direct trace verification passed with 222/222 requirements/source nodes and no
  errors. After removing task-local probe directories from `tests/`, the main-agent
  final trace contract suite passed all 40 tests in 105.54 seconds with its basetemp
  isolated under the D023 review directory.

No network, GPU, production NVMe sweep, long run, DDP/NCCL, multi-GPU validation,
