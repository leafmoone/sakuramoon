## Scope

- Reuse D010 `fetch_dataset_shard` for download, byte/SHA verification, and `.partial` publication.
- Enforce explicit low/high byte watermarks and evict the oldest unprotected manifest shard when a new shard would exceed the high watermark.
- Persist only completed shard paths, the active shard, and replay counters in one small JSON state file.
- Skip completed shards and require an interrupted active shard to be prepared first after restart. D010 opens its `.partial` with `wb`, so replay starts the shard download from byte zero.

This task intentionally implements one in-process coordinator. It does not add a daemon, service, database, cross-process lock, capability object, Range resume, prefetch state, or serialized shuffle buffer.

## Evidence boundary

Synthetic CPU tests cover explicit quota validation, LRU order, protected entries, oversized shards, state round trips, completed-shard skipping, active-shard replay order, interruption persistence, and replay sample counters.

Data package review found that state was bound only to shard paths. State schema v2
now persists the canonical immutable manifest SHA-256 and rejects reuse with any other
manifest, including a different revision with identical paths. Legacy unbound state is
not migrated silently. The independent rereview passed the remediated implementation
and traceability boundary.

The current Data package review found that a post-replace parent-directory fsync
failure could expose a new state while `save()` reported rejection. State updates now
durably link the previous inode before replacement. A failed new-state directory fsync
restores that inode and fsyncs the rollback; an initial publication failure removes the
new state and fsyncs the empty namespace. Direct fault contracts cover both branches
and leave no task-owned temporary or rollback entry. If only the already-committed
state's rollback-link cleanup fsync fails, a distinct committed-state error requires
the caller to reload instead of misclassifying the transition as rejected.

No production NVMe/network/GPU benchmark was run. The 300-500 GiB values, durable
two-worker execution, concurrent rank requests, cold-cache two-hour throughput,
ready wait, host memory, and production replay audit remain milestone evidence and are
not claimed here.
