# T045: Durable checkpoint cadence and stage budget

Status: implementation complete; independent AI/model and Infra review pending.

## Dependencies and scope

- Depends on the T044 service-decoupled raw checkpoint contract and the fixed
  1,000-successful-update/6-hour checkpoint policy.
- Upgrades only production raw continuation state. Model-only, PMA and release
  artifacts remain schema v1, and T042/T044 historical evidence is unchanged.
- Persists the absolute successful-update stage budget and the last durably
  committed checkpoint cadence using Unix wall-clock seconds.

## Contract

- Raw manifests and trainer/growth documents use schema v3. Raw schema v1/v2
  artifacts hard-fail; no implicit migration or cadence reset is allowed.
- Trainer state records exact stage start and terminal successful updates. The
  checkpoint update must remain inside that interval, and an active growth ramp
  must start at the stage origin and finish within the terminal budget.
- Trainer state records the locked 1,000-update/6-hour policy together with the
  last successful update and Unix wall-clock timestamp of the checkpoint being
  durably committed. The cadence update must equal the raw checkpoint update.
- A wall clock earlier than the persisted anchor hard-fails. Runtime code must
  not substitute a process-local monotonic timestamp or silently reset the
  six-hour window after restart.
- The proposed committed cadence is included in the raw state being published;
  in-memory cadence advances only after atomic checkpoint publication succeeds.

## Validation

- Targeted CPU schema, round-trip, legacy rejection, PMA, retention, stage,
  scheduler and runtime tests.
- Targeted one-GPU raw save/load and growth migration tests; no long run.
- Ruff, strict Pyright, traceability verification and `git diff --check`.
- Independent AI/model-correctness and Infra/performance review before closure.

Implementation and review agents do not commit. The main agent performs final
validation and creates the atomic T045 commit.
