## Implemented engineering scope

- Load one standalone strict TOML document with no production sentinel, semantic
  CLI override, distributed launch state, automatic fallback, or more than ten
  successful updates.
- Require exactly one visible CUDA device, native single-GPU execution, a 16-layer
  dense SDPA reference DiT, fixed growth alpha, and an explicit observation boundary.
- Feed generated local tar shards through the real process-isolated
  `DataServiceServer`/`DataServiceClient` lease path and exactly two spawned persistent
  DataLoader workers.
- Load the prepared local Qwen and Mage-VAE, execute the full conditioning/DiT path,
  strict JLT loss, backward, FP32 global clip, and TorchAO AdamW8bit update.
- Publish a raw `COMPLETE` checkpoint after successful update 1, release parent CUDA
  model allocations, then restore in a fresh process and complete update 2.
- Keep `sakuramoon.cli.train` unchanged and fail-closed. The dedicated engineering
  command cannot unlock, configure, or invoke production training.

## Production lifecycle extension

The production CLI now reaches strict config and static preflight instead of rejecting
all invocations at the entry point. It supports only fresh start or an exact absolute
raw `COMPLETE` resume path. Static preflight verifies single-GPU topology, governed
storage capacity, local assets, logging/checkpoint contracts and evaluator identities
before any CUDA/bootstrap/service action. The accepted path integrates the production
data stream, Qwen, VAE, 16L DiT, strict loss, backward, clip, TorchAO update, telemetry
and raw checkpoint publication.

Coordinator-only bounded acceptance passed the real first update and a separate real
service/preflight/update/raw/fresh-process N-to-N+1 test. Full details are in
`reviews/S000/production_readiness_report.md` and
`reviews/S000/production_readiness_test_report.json`.
