## Implemented engineering scope

- Load one standalone strict TOML document with no production sentinel, semantic
  CLI override, distributed launch state, automatic fallback, or more than ten
  successful updates.
- Require exactly one visible CUDA device, native single-GPU execution, a 16-layer
  dense SDPA reference DiT, fixed growth alpha, and an explicit observation boundary.
- Feed generated local tar shards through the real process-isolated
  `DataServiceServer`/`DataServiceClient` lease path and exactly two spawned persistent
  DataLoader workers.
- Load the prepared local Qwen and Mage-VAE, execute the full conditioning/DiT path,
  strict JLT loss, backward, FP32 global clip, and TorchAO AdamW8bit update.
- Publish a raw `COMPLETE` checkpoint after successful update 1, release parent CUDA
  model allocations, then restore in a fresh process and complete update 2.
- The original dedicated engineering command cannot unlock, configure, or invoke
  production training. The later production lifecycle extension is separately bounded
  by strict config and preflight.

## Production lifecycle extension

The production CLI reaches strict config and fail-closed preflight instead of rejecting
all invocations at the entry point. It supports only fresh start or an exact absolute
raw `COMPLETE` resume path. Preflight verifies single-GPU topology, governed storage,
local Qwen/VAE files, the operational manifest/validation selection, live data-service
identity, logging/checkpoint contracts and the zero-update production contract before
training. Formal evaluator identities are isolated in `eval.toml` and cannot block or
silently enter training. The accepted path integrates the production data stream, Qwen,
VAE, 16L DiT, strict loss, backward, clip, TorchAO update, telemetry and raw checkpoint
publication.

The six one-update capacity cells covered workers 1/2/3 and local batch 1/2. They selected
workers=2, ready batches=2 and local batch=2 for the current TOML; observed 3.9147
samples/s and 17.48 GB reserved memory are engineering observations, not steady-state
throughput or a formal optimum. Fresh-process resume restored RAW update 1 from an exact
absolute path, completed update 2, wrote metrics updates `[1,2]`, and retained exactly
the configured two RAW checkpoints.
